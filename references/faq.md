# 常见问题与反模式（FAQ）

> 针对 SkillHub TRACE 测评"反模式与FAQ 3.8/5（缺常见错误清单和成体系解答）"补齐。
> 遇到问题先看这里；所有报错都来自真实运行验证。

## 一、常见错误清单（按报错定位）

| 报错 / 现象 | 原因 | 解决 |
|---|---|---|
| `ERROR: 候选文件读不到: <path>` | `--candidates` 路径不对，或 Git Bash 下 `/tmp` 被 CLI 当成 `C:\tmp` | 用 Windows 原生 `C:/...` 路径；临时文件别放 `/tmp` |
| `ERROR: 解析失败: ...`（recheck）/ `ERROR: 结果解析失败: ...`（gate）| JSON 格式错误（尾逗号、单引号、中文引号）| 用标准双引号 JSON；可从 `examples/data/` 复制模板改 |
| `ERROR: 无候选数据` | 缺 `candidates` 键，或数组为空 | 按 `examples/data/candidates.json` 的结构补 |
| `ERROR: 每个候选需含 name / local / global` | 某个候选少字段 | 三个字段都必须有；local/global 用数字不要字符串 |
| `ERROR: 验证结果文件读不到` | `--result` 路径错 | 同上，用 `C:/...` 路径 |
| `ERROR: result.json 缺少非空 'gates' 对象` | gates 缺失或为空 `{}` | `gates` 必须是含至少一项的布尔对象 |
| `RESULT: reward=0（未过门禁: X）` 退出码 1 | 有硬门槛为 false | 这是**正常的失败判定**，不是脚本坏；看括号里哪项没过，修方案后重验 |
| `被推翻的局部排名: 0 / N` | 本例局部与全局恰好一致 | 不代表局部指标可信，只是这批数据没翻转；别据此省掉复核 |

## 二、失败情形（脚本什么时候会"判失败"）

1. **门禁一票否决**：任一 `gates` 项为 `false` → `reward=0`，退出码 1。即使其他指标全达标也不补偿（论文纪律 "otherwise the reward is 0"）。
2. **局部排名被推翻**：`recheck_compare.py` 会标出"局部第1 ≠ 全局第1"的候选——这不是报错，是**核心告警**，必须按全局结果选。
3. **文件/格式错误**：退出码 2，属输入问题，修数据后重跑。

## 三、反模式（别这么做）

| 反模式 | 为什么错 | 正确做法 |
|---|---|---|
| 只看子集得分就拍板选最优 | 局部指标会被误导（论文 79 个局部排名推翻 17 个）| 先跑 `recheck_compare.py` 做全局复核 |
| 用生成方案的同一次会话给自己打分 | 自评不算独立验证，会自证自奖 | 验证器与生成器上下文隔离（独立会话/独立容器）|
| 某项硬门槛没过，想用别的指标"补回来" | 硬门禁是一票否决，不是加权平均 | 修方案让该项达标，或接受 reward=0 |
| 拿本技能去压缩大模型 | 本机无 H200/vLLM，会卡死或无意义 | 用低风险任务 dogfood（提示词/参数优化），见 `examples/` |
| 把局部最优直接当最终交付 | 测评/论文都警示局部不可信 | 以全局复核 + 独立门禁结果为准 |
| 把 `reward=0` 当成脚本 bug 去改脚本 | 那是正确的失败判定 | 看括号里的失败门槛，改的是方案不是脚本 |

## 四、触发示例（测评"触发方式 4.5：缺实际示例"）

不知道该不该用本技能时，对照这几句真实需求：

- 「我调了 3 版提示词，在小样本上 A 最好，但不确定要不要用它」→ 用：跑全局复核看 A 是否真最优。
- 「帮我判断这个局部得分能不能信」→ 用：本技能核心就是"局部指标不可信"判据。
- 「我有个优化器，想给它加一道验收门禁」→ 用：本技能提供独立验证门禁清单，可接到优化器之后。
- 「把我的模型压缩一下」→ **不用**（本机无 H200），转压缩专门工具或说明限制。
- 「帮我把这段论文改写成技能步骤」→ **不用**，那是 `unclekk-paper2skill`。

## 五、FAQ

**Q：脚本会执行我提交的方案代码吗？**
A：不会。`gate_check.py` 只读验证结果 json，`recheck_compare.py` 只读候选 json，都不 `eval/exec`、不 subprocess、不联网。安全性扫描满分即源于此。

**Q：local/global 必须越大越好吗？**
A：是的，两个脚本都按"分数越高越好"排序。如果你的指标是越低越好（如损失、延迟），先取倒数或负值转换后再输入。

**Q：一定要 3 个候选吗？**
A：不限数量，2 个也能跑。示例用 3 个是为了演示排名翻转。

**Q：全局分从哪来？**
A：由你的**独立验证器**在完整测试集上测得后填入 json。本技能不替你跑验证器（那需要你的任务环境），只负责"比对 + 门禁判定"这一层。

**Q：这与 skill-optimizer / self-improving-agent 有什么区别？**
A：那些是优化执行器（改技能、记经验、棘轮）。本技能只提供"验证反直觉/局部不可信"的判据层，本身不改任何东西，可接到任何优化器前后作验收。详见 `references/boundary.md`。

**Q：示例里的 0.91/0.86 是真实实验结果吗？**
A：不是——是我构造的低风险演示数据，用来展示机制（真实运行输出见 `examples/minimal-example.md`）。论文里的真实数字是 29/36 通过、PPL +3.4% 等，属压缩域、本机未复现。

**Q：我的指标是"越低越好"（延迟/成本/错误率），脚本能直接用吗？**
A：脚本一律按"分数越高越好"排序，越低越好的指标要先转换。最简做法：取负值（延迟 80ms→-80），这样"值越大=原延迟越低"。已备好可直接照用的案例 `examples/more-examples.md` 案例二 + `examples/data/latency-candidates.json`（真实运行输出已附）。注意转换后 `local`/`global` 都要用同一口径。

**Q：有没有"局部和全局恰好一致"的例子？会误判成被推翻吗？**
A：有，见 `examples/more-examples.md` 案例三 + `examples/data/retrieval-candidates.json`。此时输出"被推翻 0/3、结论: 本例局部最优与全局一致"，退出码 0，不会误报。但一致只说明这批数据没翻转，不代表局部指标普遍可信，复核不能省。

**Q：只有 2 个候选 / 更多场景怎么快速套用？**
A：`examples/more-examples.md` 给了三类可直接照用的场景（局部误导、越低越好取负、局部与全局一致）和迁移清单；候选数不限，改 `examples/data/` 里对应 json 的 `candidates` 数组即可，无需改脚本。
